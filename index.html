0-3 分钟：开场

大家好，欢迎来到 MotrixLab 入门精品课程。

这门课面向的是想入门机器人强化学习、想读懂 MotrixLab 项目、并且希望后续能自己修改 Demo、调整奖励、开发新任务的同学。

在开始之前，我想先说明这门课的学习方式。我们不会只停留在"概念介绍"，也不会一上来就直接跑一个 Demo，然后告诉大家命令是什么。真正重要的是：我们要知道一个机器人强化学习项目是怎么组织起来的。

很多同学刚接触这类平台时，会遇到几个典型问题：

  • 训练脚本在哪里？
  • 环境代码在哪里？
  • 机器人模型在哪里？
  • 观测、动作和奖励分别在哪里定义？
  • 一个 Demo 跑起来以后，如果效果不好，应该从哪里查？

这些问题如果没有系统方法，就很容易变成到处翻文件、靠猜理解代码。

所以这门课的第一章，我们先不急着进入代码细节，而是先回答一个更基础的问题：MotrixLab 到底能做什么。

3-12 分钟：MotrixLab 的定位与应用场景

MotrixLab 可以理解为一个面向机器人强化学习的开发平台。

这里有两个关键词：机器人，强化学习。

机器人任务和普通强化学习任务不太一样。普通教学案例里，我们可能看到 CartPole、Pendulum 这类简单环境，状态空间和动作空间都比较小。但机器人任务通常要复杂得多，它涉及：

  • 机器人模型
  • 关节和执行器
  • 物理仿真
  • 接触和碰撞
  • 控制频率
  • 动作约束
  • 奖励设计
  • 训练算法
  • 日志和模型保存

这些东西加在一起，就不再是一个简单脚本能优雅解决的问题。

MotrixLab 的定位，就是把这些环节组织起来，让我们能够在一个相对标准化的框架中完成机器人强化学习任务的开发、训练和分析。

它的典型应用场景包括三类。

第一类是学习和教学。

如果你是初学者，MotrixLab 可以帮助你看到一个机器人强化学习项目应该如何拆分：环境怎么写，奖励怎么设计，配置怎么管理，训练怎么启动。

第二类是 Demo 复现和分析。

很多时候我们不是从零开始写任务，而是先看官方 Demo。比如基础控制任务、机械臂操作任务、运动机器人任务。MotrixLab 可以让我们用统一方法去分析这些 Demo：任务目标是什么，观测是什么，动作是什么，奖励是什么，终止条件是什么。

第三类是任务改造和二次开发。

当你理解了现有 Demo 以后，就可以开始做修改。比如改一个奖励项，换一个目标位置，调整动作尺度，或者基于已有任务开发一个新环境。

所以，MotrixLab 不是只让我们"运行别人写好的案例"，更重要的是帮助我们从运行案例过渡到理解案例，再过渡到改造和开发案例。

这里可以提醒学生：学 MotrixLab 的重点不是记住每一个文件名，而是掌握一套阅读和开发机器人强化学习项目的方法。

12-21 分钟：机器人强化学习平台的核心价值

接下来我们讲 MotrixLab 这类平台的核心价值。

机器人强化学习项目里，最难的往往不是某一个算法公式，而是工程组织。

假设我们要训练一个机器人完成任务，比如机械臂到达目标点，或者四足机器人保持稳定行走。我们至少要解决几个问题。

第一，环境怎么定义。

环境要告诉智能体当前看到了什么，也就是观测；还要告诉智能体可以输出什么，也就是动作；还要告诉训练算法一步执行以后发生了什么。

第二，奖励怎么设计。

强化学习没有逐步标准答案，智能体主要依靠奖励判断行为好不好。如果奖励设计不合理，模型可能学不到任务，或者学到我们不想要的行为。

第三，参数怎么管理。

机器人任务里参数非常多，比如仿真步长、episode 长度、动作缩放、奖励权重、学习率、训练步数。如果这些参数散落在代码各处，实验很难复现。

第四，训练流程怎么启动。

一次训练并不是简单调用一个函数。它通常包括命令行参数解析、配置加载、环境创建、算法初始化、训练循环、日志记录和模型保存。

第五，Demo 怎么分析。

我们拿到一个官方 Demo，不能只看它能不能跑。我们要知道它为什么能跑，任务目标是什么，奖励项是什么，哪些设计可以复用，哪些地方可以修改。

MotrixLab 的价值，就是把这些问题拆开处理。

可以用一句话总结：

MotrixLab 把机器人强化学习任务拆成环境、奖励、配置、注册和训练流程等模块，让项目更清晰、更容易扩展，也更适合教学。

这里可以给学生一个类比。

我们可以把 MotrixLab 看成一个机器人强化学习工作台。工作台上有不同区域：

  • 环境区域负责定义任务
  • 奖励区域负责给行为打分
  • 配置区域负责管理参数
  • 注册区域负责让框架找到任务
  • 训练入口负责启动完整流程

当一个任务出问题时，我们就可以按模块排查，而不是在整个项目里乱找。

21-28 分钟：课程学习路径与目标

这一门课的学习路径会按从整体到局部、从阅读到修改的顺序展开。

第一步，先理解 MotrixLab 能做什么。

这就是本章的内容。我们先建立整体印象，知道 MotrixLab 是一个机器人强化学习平台，而不是单个算法或单个 Demo。

第二步，理解基础框架和分层架构。

下一章我们会讲 MotrixLab 的整体分层：用户接口层、训练算法层、环境实现层、物理仿真层。理解分层以后，大家以后看代码就知道每个文件大概属于哪一层。

第三步，理解训练环境。

我们会重点讲 `EnvCfg`、`Env` 和 `Reward` 的关系。简单说，`EnvCfg` 管参数，`Env` 管任务逻辑，`Reward` 管学习信号。

第四步，理解奖励函数。

奖励函数是强化学习成败的关键。我们会讲奖励在训练中的作用、设计原则、常见结构，以及奖励不合理会带来什么问题。

第五步，再进入配置系统、注册系统和训练流程。

这部分会帮助大家理解一个任务如何被框架识别，训练命令如何一路走到环境创建和模型训练。

第六步，分析官方 Demo。

我们会用统一方法分析 Demo：任务目标、观测空间、动作空间、奖励设计、终止条件和可复用经验。

最终目标是让大家具备三个能力：

  • 看懂 MotrixLab 的项目结构
  • 能分析和修改官方 Demo
  • 能基于框架开发简单的新任务

0-4 分钟：开场与承接

上一章我们讲了 MotrixLab 的定位：它是一个面向机器人强化学习的开发平台，帮助我们把环境、仿真、训练、奖励和 Demo 分析组织起来。

这一章我们进一步看它的基础框架。

学习一个工程框架，最重要的不是先记住所有类名，而是先知道系统分成哪些层。因为分层决定了我们以后怎么读代码、怎么定位问题、怎么扩展功能。

如果没有分层视角，看到一个训练任务失败，我们可能会到处改：改训练脚本、改奖励、改模型文件、改算法参数。但如果有分层视角，我们会先判断问题属于哪一层。

比如：

  • 命令行参数错了，可能是用户接口层的问题。
  • PPO 配置不合理，可能是训练算法层的问题。
  • 奖励计算异常，可能是环境实现层的问题。
  • 机器人仿真不稳定，可能是物理仿真层的问题。

所以这一章我们要建立一个非常实用的框架阅读方法：先看层，再看职责。

4-10 分钟：MotrixLab 的整体分层设计

MotrixLab 的整体结构可以先概括成四层：

  • 用户接口层
  • 训练算法层
  • 环境实现层
  • 物理仿真层

这四层不是孤立的，而是从上到下协作。

用户接口层负责接收用户命令，比如训练、测试、查看模型。

训练算法层负责策略学习，比如采样、计算损失、更新网络参数。

环境实现层负责定义任务本身，比如观测、动作、奖励、终止条件。

物理仿真层负责底层物理计算，比如机器人关节、碰撞、接触和动力学。

可以在课堂上画一个从上到下的结构：

plaintext
用户接口层
训练算法层
环境实现层
物理仿真层

这张图看起来简单，但非常关键。以后分析任何文件，都可以先问：这个文件属于哪一层？它负责启动、训练、任务逻辑，还是物理计算？

分层带来的好处是职责清晰。

环境开发者主要关心任务，不需要深入修改 PPO 训练器。算法开发者主要关心训练过程，不需要知道每个机器人任务的细节。使用者通过命令行启动任务，不需要手动拼接所有底层模块。

这就是工程框架的价值。

10-18 分钟：四层职责详解

先看第一层：用户接口层。

用户接口层是学生最容易接触到的一层。常见入口包括 `train.py`、`play.py`、`view.py` 这类脚本。

它们的职责不是实现所有任务逻辑，而是负责启动流程。比如：

  • 读取命令行参数
  • 判断要训练哪个任务
  • 选择训练框架
  • 加载配置
  • 创建环境
  • 启动训练或测试流程

所以以后如果你想知道"这个任务怎么跑起来"，应该先看用户接口层。

第二层是训练算法层。

这一层关心的是强化学习算法如何工作。比如使用 PPO 时，它要完成数据采样、优势估计、策略损失、价值损失、熵奖励、参数更新等工作。

在 MotrixLab 中，训练算法层可能对接不同训练后端，例如 SKRL 或 RSLRL。不同后端内部实现不同，但它们都需要和环境交互。

这里要强调一个接口思想：训练算法不应该直接关心机器人细节。它只需要环境返回标准强化学习信息：观测、奖励、终止标志等。

第三层是环境实现层。

这是本课程后面最重要的一层。环境实现层主要包括 `EnvCfg`、`Env` 和 `Reward`。

`EnvCfg` 定义环境参数。比如模型文件、仿真步长、episode 长度、动作范围、奖励权重等。

`Env` 实现任务逻辑。比如如何接收动作，如何推进仿真，如何构造观测，如何判断任务结束。

`Reward` 负责生成学习信号。它告诉智能体当前行为是否更接近任务目标。

很多训练失败的问题，其实都发生在这一层。比如观测缺关键信息、动作尺度不合理、奖励方向错误、终止条件过严。

第四层是物理仿真层。

这一层负责让机器人真的"动起来"。它处理机器人模型、关节、碰撞、接触、质量、惯性、动力学和仿真步进。

如果机器人一开始就抖动、穿模、爆炸，或者动作完全不符合物理直觉，不能只看奖励函数，也要检查物理仿真层。

18-25 分钟：各层之间的关系

接下来我们把四层串成一个完整训练流程。

一次训练通常从用户命令开始。用户在命令行指定要训练哪个任务、使用哪个训练框架、训练多少步、是否开启可视化等。

用户接口层收到命令以后，会解析参数，然后通过注册和配置系统找到对应任务。

接着训练算法层被初始化。它会创建策略网络、价值网络、优化器和训练器。

然后环境实现层被创建。环境根据 `EnvCfg` 加载模型和任务参数，准备好观测、动作、奖励和终止逻辑。

训练开始后，算法输出动作，环境接收动作并交给物理仿真层推进。仿真层返回新的物理状态，环境再根据状态计算观测和奖励，训练算法拿到反馈后更新策略。

可以把这一过程总结成：

plaintext
用户命令
-> 训练入口
-> 配置和注册
-> 环境创建
-> 算法采样
-> 物理仿真
-> 奖励反馈
-> 策略更新

这个流程有助于排查问题。

如果环境创建失败，要看配置、注册和模型路径。

如果动作没有效果，要看动作映射、控制接口和物理仿真。

如果 reward 异常，要看奖励函数和环境状态。

如果训练曲线不收敛，要综合看奖励、观测、动作和算法参数。

所以各层之间既有清楚边界，又形成完整闭环。

第一章：训练环境的「三位一体」

1.1 核心概念

在机器人强化学习任务中，训练环境由三个模块组成：

code

1.3 为什么需要分离？

很多初学者会把所有逻辑写在一个大文件里，导致：

  • ❌ 改参数要改代码
  • ❌ 不同实验难以对比
  • ❌ 代码难以复用和测试

分离的好处：

  • ✅ 参数和逻辑分离，实验更灵活
  • ✅ 同一环境，不同配置
  • ✅ 方便调试和测试

4.3 奖励设计六大原则

#### 原则一：目标一致

python
# ❌ 错误：任务要求抓住物体，只奖励接近
reward = -distance_to_object

# ✅ 正确：接近 + 抓取双重奖励
reward = -distance_to_object + grasp_success * 10.0

#### 原则二：信号密度

python
# ❌ 稀疏奖励：只有成功时给 1，其他全 0
reward = 1.0 if task_success else 0.0

# ✅ 密集奖励：每一步都有反馈
reward = -distance_delta * 5.0      # 靠近了给奖励
       + action_smoothness * 0.1     # 动作平滑给奖励
       + (1.0 if success else 0.0)   # 成功额外奖励

#### 原则三：尺度合理

python
# ❌ 错误：惩罚量级太大，模型学会不动
reward = -100.0 * abs(action)  # 模型会直接不动

# ✅ 正确：量级相当
reward = -0.01 * sum(action**2)  # 适度的平滑惩罚
    + success_bonus              # 成功奖励

#### 原则四：防止漏洞

python
# ❌ 漏洞：奖励末端速度，模型学会抖动
reward = abs(velocity)  # 抖动也能得高分

# ✅ 修复：同时惩罚抖动
reward = abs(velocity) - 0.1 * abs(velocity_delta)

4.4 常见奖励结构

python
def compute_reward(self):
    # 任务奖励
    task_reward = -self.pole_angle ** 2 - self.cart_position ** 2

    # 成功奖励
    success_bonus = 10.0 if self.is_success else 0.0

    # 稳定性奖励
    stability_reward = -0.01 * sum(self.joint_velocities ** 2)

    # 动作惩罚
    action_penalty = -0.01 * sum(self.actions ** 2)

    # 失败惩罚
    failure_penalty = -10.0 if self.is_failed else 0.0

    # 总奖励
    total = (task_reward + success_bonus + stability_reward
             + action_penalty + failure_penalty)

    return total, {
        'task': task_reward,
        'success': success_bonus,
        'stability': stability_reward,
        'action_penalty': action_penalty,
        'failure': failure_penalty
    }

    + success_bonus      # 成功奖励

    - energy_penalty     # 能耗惩罚

# 1. 定义配置
from dataclasses import dataclass
from motrix_envs.registry import envcfg

@envcfg("cartpole")
@dataclass
class CartpoleCfg:
    # 仿真参数
    sim_dt: float = 0.005
    ctrl_dt: float = 0.02
    max_episode_steps: int = 500

    # 任务参数
    goal_position: float = 0.0
    initial_state_range: float = 0.05

    # 奖励权重
    action_cost_weight: float = 0.001
    velocity_cost_weight: float = 0.0
    position_cost_weight: float = 1.0

# 2. 实现环境
from motrix_envs.base import BaseEnv

class CartpoleEnv(BaseEnv):
    def __init__(self, cfg: CartpoleCfg):
        super().__init__(cfg)
        # 加载模型、创建仿真等

    def reset(self):
        # 重置环境，返回初始观测
        obs = self._get_observation()
        return obs

    def step(self, action):
        # 执行动作
        self._apply_action(action)
        self._simulate()

        # 获取观测
        obs = self._get_observation()

        # 计算奖励
        reward, reward_info = self._compute_reward(action)

        # 判断终止
        terminated = self._is_terminated()
        truncated = self._is_truncated()

        return obs, reward, terminated, truncated, reward_info

    def _compute_reward(self, action):
        # 奖励计算
        reward = -self.pole_angle**2 - self.cart_position**2
        reward -= self.cfg.action_cost_weight * sum(action**2)

        info = {
            'pole_angle': self.pole_angle,
            'cart_position': self.cart_position
        }
        return reward, info

第六章：常见问题排查

6.1 完全学不会？

检查项可能原因解决方案
reward 太稀疏随机探索很难成功加入中间奖励
observation 缺信息看不到目标检查 observation
action 没作用控制接口没接好检查 action mapping
done 太早一上来就失败放宽终止条件

6.2 学到奇怪行为？

检查项可能原因解决方案
奖励有漏洞可以作弊得分补充约束项
辅助奖励太高刷辅助项就能高分降低辅助项权重
动作惩罚太弱抖动也能接受加大惩罚

6.3 训练不稳定？

检查项可能原因解决方案
reset 随机太大每次差异大减小随机范围
sim_dt 不合理仿真不稳定调整步长

我们知道强化学习的要素首先包含5个基本元素：agent, env, obs, reward, action。除此之外，我们需要还关注初始状态和终止状态（终止条件）。因为这两点直接关乎任务完成，我们需要明确任务是从什么情况下开始的并在什么情况下结束。

在实际实现中，为了增强策略的鲁棒性和泛化性，reset 时会对初始状态和任务目标进行一定的随机化，此操作被称为域随机化（Domain Randomization）。

基本元素解释备注
环境与 agent（组成场景）agent 和环境构成了强化学习中的场景，agent 是我们要控制的机器人，环境就是机器人需要交互的对象

域随机化对初始状态和环境参数、任务目标等进行一定范围的随机，以增强策略的鲁棒性

二、任务环境详解

倒立摆 (CartPole)

#### 1. 了解任务

任务描述：一根杆子通过铰链连接在小车上。智能体需要通过给小车施加左右方向的力，让杆子保持直立不倒。

预期训练结果：

  • 杆子角度大部分时间保持在 ±5 度以内
  • Episode 时长接近或超过 10 秒
  • 小车在合理范围内移动以保持平衡

倒立摆任务可被称为 RL 界的 "Hello World"，是几乎所有强化学习研究人员接触的第一个环境。由于它的状态维度低、动力学极其简单且奖励机制非常密集，可以在极短的时间完成训练和测试。

def update_state(self, state: NpEnvState):
    # 角度标准化 (Angle Wrapping)
    angle_wrapped = (angle + np.pi) % (2 * np.pi) - np.pi

    upright = (1.0 + np.cos(angle_wrapped)) * 0.5  # 直立奖励
    ctrl = data.actuator_ctrls[:, 0]                # 当前动作
    prev_ctrl = state.info.get("prev_ctrl", np.zeros_like(ctrl))
    ctrl_delta = ctrl - prev_ctrl                   # 平滑度
    vel_penalty = 0.2 * (ang_vel**2)                # 速度惩罚

    # 能量奖励
    energy = 0.5 * ang_vel**2 + (1.0 + np.cos(angle_wrapped))
    energy_target = 2.0
    energy_reward = reward_utils.tolerance(
        energy, bounds=(energy_target, energy_target), margin=2.0,
        value_at_margin=0.1, sigmoid="gaussian",
    )

    reward = (3.0 * upright + energy_reward - vel_penalty
              - 0.001 * ctrl**2 - 0.001 * ctrl_delta**2).astype(np.float32)

最终奖励各部分：

  • 3.0 * upright：姿态分（权重最大，引导身体保持垂直）
  • energy_reward：能量分（引导系统将能量维持在直立所需的水平）
  • vel_penalty：速度惩罚（防止高速转动）
  • 0.001 * ctrl²：能耗惩罚（鼓励用最小的力气完成任务）
  • 0.001 * ctrl_delta²：平滑度惩罚（惩罚高频震荡）

tolerance 容差函数：它将物理世界中各种连续状态（距离、角度、能量等），转化为位于 [0, 1] 之间的平滑奖励信号。相比二元稀疏奖励（只有刚好命中目标才给分），tolarence 函数用高斯函数建模，把一个"硬性"的目标区间变成平滑过渡的"软性"奖励山峰。

def update_state(self, state: NpEnvState):
    tip_pos = self._tip.get_pose(data)
    target_pos = self._target.get_pose(data)
    dist_to_target = np.linalg.norm(tip_pos[:, :3] - target_pos[:, :3], axis=-1)

    # 基础稀疏奖励（margin=0 → 阶跃函数，没进圈=0分，进了圈=1分）
    base_rwd = reward.tolerance(dist_to_target, bounds=(0, self._target_radius),
                                margin=0, value_at_margin=0.0, sigmoid="linear")

    in_target = dist_to_target < self._target_radius
    continuous_reward = 0.1 * in_target

    # 连续引导性奖励
    distance_reward = 0.3 * (1.0 - np.clip(dist_to_target / 2.0, 0, 1.0))

    # 速度惩罚
    dof_vel = data.dof_vel
    vel_magnitude = np.mean(np.abs(dof_vel), axis=-1)
    velocity_penalty = 0.01 * np.maximum(0, vel_magnitude - 2.0)

    rwd = base_rwd + continuous_reward + distance_reward - velocity_penalty

三、小规模状态空间与动作空间分析

尽管倒立摆、单摆和双连杆都属于极低维度的基础任务，但它们绝不是简单的重复。这三个环境层层递进，不仅涵盖了机器人控制中的真实问题，更为我们展现了在强化学习中设计状态（State）与动作（Action）空间的典型思路。

三大任务的控制难点与异同点剖析

共同面临的真实控制难点：

  • 开环不稳定性：系统在缺乏持续且精准的外部控制时，会迅速偏离目标状态
  • 欠驱动特性：系统的控制输入维度少于其自由度（倒立摆 2 个自由度 1 个输入，双连杆 2 个自由度 1 个输入）
  • 非线性动力学：包含旋转关节的系统，其运动涉及非线性耦合

小规模状态空间的设计总结

  • 必须包含"位置"与"速度"：仅有位置/角度是不够的，为了让智能体判断系统未来的运动趋势，状态空间中必须同时包含位置信息和速度信息
  • 连续周期量的几何编码：当关节可以在 [-π, π] 之间连续旋转时，直接输入角度会有数值跳变（从 π 跳到 -π），典型做法是将标量角度 θ 拆解为 cos(θ) 和 sin(θ) 两个维度

小规模动作空间的设计总结

  • 归一化与裁剪：策略通常输出处于 [-1.0, 1.0] 的标准区间，在环境内部通过线性映射转换为真实的物理控制量
  • 连续动作 vs 离散动作：连续控制允许输出更平滑、微小的调节力矩，在机器人底层运动控制中不可或缺

基础控制任务虽然结构极简，但其对于状态变量的选择、数值跳变的处理、以及动作的归一化映射，完全可以直接套用在数十个自由度的四足机器狗或人形机器人身上。理解了这三个任务，就相当于掌握了机器人强化学习环境搭建的通用范式。

（2）机械臂控制任务的 RL 核心难点

#### 庞大的状态空间

状态空间：观测必须包含本体特征（各关节角度、角速度）、末端特征（TCP 位置、姿态）、目标物体特征（方块的位置、姿态）以及它们之间的相对几何关系。

初始状态敏感性：不同的初始位姿会对任务成功率产生巨大影响，训练中往往需要引入域随机化来提升策略鲁棒性。

#### 多样的动作设计

机械臂任务通常需要同时控制 6-8 个维度的动作。动作维度的增加会导致探索空间呈指数级膨胀。

机械臂本体的三个控制维度：

控制维度内容说明
关节空间 vs 笛卡尔空间关节控制agent 直接输出对每个具体关节的控制指令，最贴近底层物理硬件
末端控制Agent 输出末端 TCP 在三维空间中的 6 维位姿，通过逆运动学（IK）解算为各关节指令，更符合人类操作直觉
位置、速度 vs 力矩位置控制直接指定目标位置，底层 PD 控制器负责计算力矩，在强化学习中最常用、最容易收敛
速度控制指定各关节或末端的运动速度，适用于连续且平滑的轨迹跟踪
力矩控制直接输出电机力矩，难度最高，但能实现最柔顺的接触力控制
绝对控制 vs 增量控制绝对控制每次输出一个全局坐标或绝对角度
增量控制每次输出相对于当前状态的微小偏移量。在强化学习中往往表现更好，能有效缩小探索范围，大幅降低学习难度

本体与末端执行器的异构控制：

  • 关节类型不同：机械臂本体是旋转关节，夹爪是平移关节
  • 动作映射逻辑不同：本体和夹爪需要完全不同的控制逻辑（如本体用笛卡尔增量控制，夹爪用二元开闭控制）

#### 多阶段奖励调优

机械臂任务通常包含多个存在因果依赖的阶段：

  • 稀疏奖励失效：只有当方块被举起时才给奖励，Agent 极难在随机探索中偶然完成一连串正确动作
  • 多阶段奖励复杂平衡：必须为每个阶段设计连续稠密奖励，阶段转换往往是训练的瓶颈（"卡点"）
  • 防止奖励作弊：如果"接近"奖励太高而"抓取"奖励太小，Agent 可能学到一直悬停在方块正上方蹭接近奖励

def apply_action(self, actions: np.ndarray, state: NpEnvState):
    # 机械臂本体：增量位置控制
    old_joint_pos = self.get_dof_pos(state.data)[:, : self._action_dim - 1]
    new_joint_pos = actions[:, : self._action_dim - 1] + old_joint_pos  # action as offset

    # 夹爪：Sigmoid + 伯努利采样
    probabilities = 1 / (1 + np.exp(-actions[:, -1]))
    sampled_gripper_action = np.where(
        probabilities > np.random.rand(*probabilities.shape), 0, 0.04
    )[:, None]  # Close 0, Open 0.04

    new_pos = np.concatenate([new_joint_pos, sampled_gripper_action], axis=-1)
    cliped_new_pos = np.clip(new_pos, self.joint_pos_min_limit, self.joint_pos_max_limit)
    state.data.actuator_ctrls = cliped_new_pos
    return state

奖励（修改后版本，含进度奖励和静止奖励）：

python
def _compute_reward(self, state: NpEnvState, truncated: np.ndarray):
    hand_pos = self.hand.get_pose(state.data)[:, :3]
    cube_pos = self._cube.get_pose(state.data)[:, :3]
    hand_cube_distance = np.linalg.norm(cube_pos - hand_pos, axis=-1)

    # 接近奖励
    reach_reward = 1 - np.tanh(hand_cube_distance / 0.1)

    # 提升奖励
    lift_height = cube_pos[:, 2]
    lifted = lift_height > 0.04

    # 目标跟踪
    object_command_dist = np.linalg.norm(cube_pos - state.info["commands"], axis=-1)
    command_progress = object_command_dist / state.info["command_cube_max_length"]
    command_progress_reward = (1 - np.tanh(command_progress / 0.4))
    command_tracking_reward = (1 - np.tanh(object_command_dist / 0.3)) * lifted * (hand_cube_distance < 0.02)
    command_reaching_reward = (1 - np.tanh(object_command_dist / 0.05)) * (object_command_dist < 0.3) * (hand_cube_distance < 0.02)

    # 惩罚项
    action_diff_sq = np.sum(np.square(state.info["current_actions"] - state.info["last_actions"]), axis=-1)
    joint_vel_sq = np.sum(np.square(self.get_dof_vel(state.data)[:, :self._num_dof_vel]), axis=1)

    # 到达目标后静止奖励
    end_still_reward = (1 - np.tanh(joint_vel_sq / 0.4)) * (object_command_dist < 0.04)

    # 奖励权重
    reward = (
        1.0 * reach_reward
        + 10 * lifted * (hand_cube_distance < 0.05)
        + 100 * command_progress_reward * lifted
        + 20 * command_tracking_reward
        + 220 * command_reaching_reward
        - action_penalty_weight * action_diff_sq
        - joint_vel_penalty_weight * joint_vel_sq
        - 1e-2 * joint_dof_sq
        + 50 * end_still_reward
    )

运动机器人 Demo 讲解：Walker / GO1 / Humanoid

核心目标

在 MotrixLab 的 `motrix_envs` 中，提供了多种预置的运动机器人环境，最典型的是：

  • Walker（双足步行者）—— 来自 DeepMind Control Suite
  • GO1（Unitree Go1 四足机器人）
  • Humanoid（人形机器人）—— 来自 DeepMind Control Suite

它们都依赖本体感受（关节位置、速度等）进行控制，目标是在平坦或者复杂地形上稳定、快速地前行，并且尽量避免摔倒。

Walker 和 Humanoid 是来自 DeepMind Control Suite 的经典任务，包括了 stand、walk、run 三个难度递进的任务。

本章节的目的是让大家能够详细深入了解这三类机器人的强化训练过程，了解三种不同形态的 agent 同样完成相同的 RL 训练行走过程中的相同点和不同点，并且由于形态、奖励设计、控制策略等的差异，训练难度和方法都会有些不同。

11.1 机器人行走任务的共性与差异

11.1.1 共性

三个任务无论是行走、稳定站立还是奔跑，这个训练过程都有一个统一确定的 RL 框架，并且是连续控制的过程，而不是离散的。

统一的 RL 训练框架概括为：先看周围（观测维度中的状态）→ 进行决策动作 → 这个动作在物理引擎算一步（仿真）→ 系统告诉你是否做得好（奖励）或是否失败了（终止）。

在 MotrixLab 里，每一帧环境都会返回一个观测向量，这就是策略"看周围"的唯一信息来源。

对于行走任务，观测通常不包含视觉，而是本体感受式的，比如：

  • 所有关节的当前位置
  • 关节速度
  • 身体基座的线速度和角速度
  • 重力方向在基座坐标系下的投影
  • 上一帧的动作，帮助感知自己刚才做了什么
  • 命令速度

这些不同来源的信息会被拼接成一个一维浮点数数组，作为策略网络的输入。

策略网络拿到观测向量后，会输出一个动作分布。因为我们做的是连续控制，所以策略通常输出的是一个多维高斯分布的均值与标准差，然后在这个分布里采样得到具体的动作向量。

动作 action 被应用到机器人的关节上之后，MotrixSim 物理引擎就会执行一个仿真步，解算整个机器人的刚体动力学，算出下一时刻的身体位置、关节角度、接触力、碰撞情况等等。

三个机器人的物理模型不一样，但 MotrixLab 对它们的仿真接口完全一致：都是"给定动作 → 推进仿真 → 返回新状态"。

仿真结束后，环境会根据当前状态计算出一个即时奖励，并判断是否触发终止条件。

整个"观测→动作→仿真→奖励"的循环，在不同机器人之间，只是维度数字和奖励权重不同，循环本身的代码结构与数据流动方向是完全统一的。正因为有这个统一，MotrixLab 才能用一个 `train.py` 脚本，只通过切换环境名 `--env walker`、`--env go1`、`--env humanoid`，就完成三个任务的训练。

11.1.2 差异

差异主要来自三件事：机器人形态、环境复杂度、奖励与终止设计。

1. 机器人形态差异（2D 双足 vs 3D 人形 vs 4足）

自由度62112
动作维度62112
观测维度245948
形态2D 平面3D 空间3D 空间四足
  • Walker 自由度少、观测少，动作维度固定，为最简单的行走任务
  • Humanoid 自由度非常高（21维），动作多，目标姿态区域为强约束的非凸空间
  • GO1 动作维度居中，但需处理四足步态协调（如 trot、pace、bound）

2. 环境从简到繁递进

WalkerHumanoidGO1

3. 奖励结构差异

  • Walker：以站稳为主，再乘一个前进奖励，结构简单易学
  • Humanoid：posture × speed × energy × gait 的乘法结构，任何一项差都会明显拉低总回报，学出来更"像人走路"，但训练更难
  • GO1：大量加权项（速度跟踪、姿态、扭矩、动作变化率、四足腾空时间等）

4. 终止条件差异（严格程度不同）

  • Walker：主要以数值异常（NAN）终止，比较宽松
  • Humanoid：头高、躯干直立度、速度极值、数值有效性多条件终止，更严格
  • GO1：机身躯干与地面接触即终止，更贴近四足防摔逻辑

5. 任务驱动方式差异（速度参数 vs 速度指令）

  • Walker / Humanoid：通过固定 move_speed 定义任务难度档位
  • GO1：每次 reset 随机采样速度指令 commands，策略学的是"步态跟踪"

11.2 稳定性、接触、平衡与协调控制

要理清训练过程完整的数据流向：任务 cfg 被注册 → 通过装饰器 registry 被调用 → 该类被存进全局字典中。同理任务环境类、RL 算法也是这样被注册的。随后我们启动训练，装饰器被调用，系统会自动判断推理框架。

RL cfg 的修改会影响 RL 的训练过程（训练算法本身的超参数），改任务的 cfg 会影响环境本身（比如训练的目标、奖励等）。

---

11.3 复杂运动任务中的训练挑战

不同任务的训练时间根据复杂程度的不同而不同。

1. 奖励权重设计不合理

以 2D Walker 举例，如果修改站立和前进的奖励比重，可能会学不会前进的行为，只会在原地打转。

2. 观测空间维度不够

减少关键的观测空间的信息，可能会出现训练很慢以及训练后的效果不稳定的情况。

3. 终止条件过松或过严

  • 过松：agent 学不会策略，一直摔倒
  • 过严：agent 不敢尝试，一直在原地，几乎学不了任何东西

4. 神经网络大小不匹配

  • 太小的神经网络容易陷入局部最优，对于长程任务来说容易找不到最优解
  • 太大的神经网络容易过拟合，泛化能力变差

环境创建

def train(self) -> None:
    rlcfg = self._rlcfg
    env = env_registry.make(self._env_name, sim_backend=self._sim_backend, num_envs=rlcfg.num_envs)
    set_seed(rlcfg.seed)
    skrl_env = wrap_env(env, self._enable_render)
    models = self._make_model(skrl_env, rlcfg)
    ppo_cfg = _get_cfg(rlcfg, skrl_env, log_dir=get_log_dir(self._env_name))
    agent = self._make_agent(models, skrl_env, ppo_cfg)
    cfg_trainer = {
        "timesteps": rlcfg.max_batch_env_steps,
        "headless": not self._enable_render,
    }
    trainer = SequentialTrainer(cfg=cfg_trainer, env=skrl_env, agents=agent)
    trainer.train()

`env_registry.make()` 流程：

  1. 查 `_envs` 注册表

  4. 构造环境类，传入 `num_envs`

训练执行（SKRL PPO 循环）

组件组装后，训练逻辑（由 SKRL 内部驱动，MotrixLab 不手写）：

  1. 并行 `num_envs` 个环境 `step`
  2. 收集 `rollouts` 步经验写入 `memory`
  3. 做 `learning_epochs` 轮 mini-batch 更新（PPO clip、value loss、entropy 等）

注册时覆盖

注册系统：新环境如何接入框架

注册系统的作用

MotrixLab 有两套注册表，分工不同：

  1. `motrix_envs.registry`（仿真环境）

- 用字符串 `name`（例如 `"cartpole"`）绑定：环境配置类（`EnvCfg` 子类）和环境实现类（`ABEnv` 子类）

- 对外统一入口是 `make(name, sim_backend=..., env_cfg_override=..., num_envs=...)`

- 作用：把「环境名字」解析成可运行的环境对象

  1. `motrix_rl.registry`（RL 训练配置）

- 用同一个环境名字 `env_name`，在框架名（当前固定为 `"skrl"`）和训练后端（`"jax"` / `"torch"`）下注册 PPO 等训练超参的 dataclass

- `default_rl_cfg(env_name, "skrl", backend=...)` 会按后端优先选专用配置

- 作用：把「环境名字 + 训练后端」解析成默认 RL 超参

必须实现的三个抽象方法：

  1. `apply_action(actions, state)` — 将动作写进仿真
  2. `update_state(state)` — 读取新状态（obs / reward / terminated）
  3. `reset(data)` — 重置环境并返回初始 obs

一步 `step` 的内部顺序：

python
def step(self, actions):
    self._prev_physics_step()                    # 清空上一步的 reward/terminated
    self._state = self.apply_action(actions, self._state)  # 将动作写进仿真
    self.physics_step()                          # 物理步
    self._state = self.update_state(self._state) # 读新状态 obs/reward/terminated
    self._state.info["steps"] += 1
    self._update_truncate()                      # 按 max_episode_steps 设 truncated
    self._reset_done_envs()                      # 已结束的 env 做 reset()

如何让新任务被框架"自动识别"

"自动识别"是什么

MotrixLab 不会扫描目录、读配置文件列表。所谓"自动识别"，指的是：Python 在 import 某个包/模块时，执行类定义上的装饰器，把条目写进内存里的两个字典；之后脚本根据字符串名字去查字典。

因此新任务要能被 `train.py` / `view.py` / `play.py` 用上，必须同时满足：

  1. 装饰器已执行（模块被 import 过）
  2. CLI 里的 `--env` 字符串与注册名完全一致
  3. 训练/回放时：环境注册 + RL 注册都存在（`view` 只需环境注册）

接入新任务的具体步骤

假设新任务注册名为 `my-task`：

步骤 1：实现并装饰

  • `@registry.envcfg("my-task")`
  • `@registry.env("my-task", "np")`

步骤 2：接上 import 链（核心）

任选一种：

A. 挂到现有分类（推荐）

code
# motrix_envs/basic/__init__.py 增加：
from . import cartpole, ..., my_task  # noqa: F401

# motrix_envs/basic/my_task/__init__.py
from . import my_task_np  # noqa: F401

B. 新建顶层分类

code
# motrix_envs/__init__.py
from . import basic, locomotion, manipulation, my_category  # noqa: F401

步骤 3：RL 配置 + 保证会被加载

在 `motrix_rl/cfgs.py`（或你新建但被 `motrix_rl/__init__.py` import 的模块）里：

python
@rlcfg("my-task")
@dataclass
class MyTaskPPO(PPOCfg):
    ...

步骤 4：用同一字符串跑命令

bash
uv run scripts/train.py --env my-task
uv run scripts/view.py --env my-task

注意：名字区分大小写；`my-task` 与 `my_task` 是两个不同 key。

各入口脚本如何"认出"任务名

  • `train.py`：先加载 rl cfg 注册 RL，再 `default_rl_cfg(...)` 获取配置，最后 `env_registry.make(...)` 建环境
  • `view.py`：只走 `registry.make(env_name, ...)`，不查 RL 表
  • `play.py`：同 `train`，通过 `ppo.Trainer`；策略文件按环境名找 checkpoint：`runs/{env_name}/` 下找最新 `best_agent.*`

调整运动速度

可以把平稳的步态变成蹦蹦跳跳前进的。

12.3 后续学习与实践建议

做好记录和版本管理

在完成一个大的项目的时候不要怕出错，大胆尝试！但是在这个过程中一定要做好记录和版本管理。因为实际你去调试一些奖励或者调整超参，并不知道这些修改是否奏效，如果不奏效那之前的版本参数就很重要了。但这时候你修改太多根本无法记住之前的版本，所以做好版本管理很重要。

推荐一个小习惯：每次跑实验之前，在项目目录里建一个文件夹，随手写一个 `exp_log.md`——不一定很正式，就是记几行：

  • 今天改了什么参数（比如把速度奖励权重从 1.0 调到 2.0）
  • 预期会看到什么变化（希望机器人步幅变大）
  • 实际跑下来看到什么效果（1000步后开始同手同脚）

这个简单的记录，积累几个星期，你对这个任务的直觉就会飞速增长。因为开始把参数改动和行为变化之间建立了因果映射，而不再是黑盒调参。

多写注释

多写注释帮助自己理解整体的项目框架。

训练技巧

训练时可以并行少量 env 渲染，观察单 env 行为以便调试。训练期间可以并行只开 1-2 个环境渲染出来，单独观察一个机器人的行为，看到训练过程中每一次尝试后的机器人是否朝着奖励策略的方向改进。

加载自己的机器人模型

当你对框架足够熟悉之后，下一步就可以大胆尝试：搭建自己的地图，加载自己的机器人模型。

MotrixLab 内部有一个很大的优势——MotrixSim 引擎的优化极大降低了仿真的硬件门槛。它的算力消耗仅为国外同类产品的十分之一，所以即使你用的普通的电脑，也能跑得动训练任务。这就意味着你不需要一个 4090 才能做机器人仿真。

具体操作步骤：

  1. 找一个现成的机器人 URDF
  2. 复制一份距离你想要的目标最近的现有任务（比如你想做一个四足机器人，就从 GO1 或者 GO2 的任务文件开始改）
  3. 替换模型路径、关节名、默认姿态、PD 参数等信息，在注册表里用 `@registry.envcfg("my-robot")` 注册一个新名字
  4. 先别调奖励，先跑通环境，用 `view.py` 看一下模型能不能正常导入、关节能不能动、碰撞体对不对
  5. 等环境能稳定交互了，再开始奖励调参，逐步让机器人学会站立、行走

这个路径一旦走通，你就不再是强化学习的"旁观者"，而是能独立设计和闭环的开发者了。MotrixLab 也会成为趁手的工具，后面就可以尝试 sim2real，将自己在仿真中设计的应用在真机中啦！

第一期核心修正案例

问题根源：原版 Motrix 以 actuator_ctrl_limits（物理限位）作为动作空间边界，配合 action_scale=0.05。后续调参时将 action_scale 改为 0.25，但未同步修改动作空间边界。

实际影响：calf 关节动作空间异常（范围全为负值），与归一化动作空间语义不等价。

修正方案：

python
# 修正前：以物理限位作为边界
gym.spaces.Box(actuator_ctrl_limits[0], actuator_ctrl_limits[1], ...)

# 修正后：固定归一化范围
gym.spaces.Box(-np.ones(n), np.ones(n), ...)
