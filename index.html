课程导论：MotrixLab 能做什么
30 分钟 导论

学习重点

  • 机器人强化学习平台的核心价值
  • 课程学习路径与目标

MotrixLab 的定位

MotrixLab 是面向机器人强化学习的开发平台。机器人任务和普通强化学习任务不太一样，它涉及：机器人模型、关节和执行器、物理仿真、接触和碰撞、控制频率、动作约束、奖励设计、训练算法、日志和模型保存。

典型应用场景包括三类：学习和教学、Demo 复现和分析、任务改造和二次开发。

平台核心价值

MotrixLab 把机器人强化学习任务拆成环境、奖励、配置、注册和训练流程等模块，让项目更清晰、更容易扩展，也更适合教学。可以把 MotrixLab 看成一个机器人强化学习工作台：

  • 环境区域负责定义任务
  • 奖励区域负责给行为打分
  • 配置区域负责管理参数
  • 注册区域负责让框架找到任务
  • 训练入口负责启动完整流程

基础框架总览：分层架构怎么看
30 分钟 架构

四层架构

架构
用户接口层    ← train.py / play.py / view.py
训练算法层    ← PPO / A3C / SKRL / RSLRL
环境实现层    ← EnvCfg / Env / Reward
物理仿真层    ← 机器人模型 / 关节 / 碰撞 / 动力学

各层职责

  • 用户接口层：读取命令行参数、选择训练框架、加载配置、创建环境、启动训练
  • 训练算法层：数据采样、优势估计、策略损失、价值损失、熵奖励、参数更新
  • 环境实现层：EnvCfg 定义参数，Env 实现任务逻辑，Reward 生成学习信号
  • 物理仿真层：处理机器人模型、关节、碰撞、接触、质量、惯性、动力学

训练流程

流程
用户命令 → 训练入口 → 配置和注册 → 环境创建
  → 算法采样 → 物理仿真 → 奖励反馈 → 策略更新

03
训练环境：EnvCfg、Env、Reward 的关系
30 分钟 环境

三个类的角色

类角色核心职责
EnvCfg环境配置类定义环境参数：观测维度、动作维度、仿真步长、episode 长度等
Env环境实现类实现任务逻辑：接收动作、推进仿真、构造观测、判断终止
Reward奖励计算类根据环境状态计算奖励，驱动智能体学习

分离设计的好处

  • 让配置可复用，同一套配置可以对应不同的实现变体
  • 让实验参数集中管理，方便调参和复现
  • 降低环境实现的复杂度，Env 只关心逻辑，不关心参数默认值

04
奖励函数：为什么奖励决定训练成败
30 分钟 奖励

奖励设计三原则

  1. 可区分性：好的奖励应该能区分不同行为的质量
  2. 可达成性：奖励信号应该引导智能体逐步接近目标
  3. 鲁棒性：奖励设计应该对环境的随机性和扰动具有容忍度

稀疏奖励 vs 稠密奖励

类型特点适用场景
稀疏奖励只在关键节点给奖励，其他时刻为0目标明确、探索空间小的任务
稠密奖励每一步都有奖励信号，引导性强复杂任务、需要精细控制的场景

05
配置系统：环境配置与训练配置怎么协作
30 分钟 配置

EnvCfg 与 RLCfg 的职责分工

配置类职责示例参数
EnvCfg环境相关配置仿真步长、episode长度、观测维度、动作维度、奖励权重
RLCfg训练算法配置学习率、批量大小、训练步数、网络结构、PPO参数

为什么解耦？

  • 环境开发者和算法开发者可以独立工作，互不干扰
  • 同一环境可以搭配不同算法做对比实验
  • 配置更清晰，不会因为参数混在一起而难以调试
  • 方便做超参数搜索，只需要改 RLCfg

训练流程：从 train.py 到模型保存
30 分钟 训练

训练流程图

流程
CLI 解析 (argparse)
  -> 确定 env_name = "cartpole"
  -> 加载 RLCfg (默认配置 + 命令行覆盖)
  -> 通过注册表找到 EnvCfg
  -> 创建 Env (根据 EnvCfg 参数)
  -> SKRL 包装 (VecEnv 等)
  -> 构建 Agent (PPO 等算法)
  -> 创建 Trainer
  -> trainer.train() 执行训练循环
  -> 定期保存模型 checkpoint
  -> 训练结束，保存最终模型

训练命令示例

bash
# 训练 CartPole
uv run scripts/train.py --env cartpole

# 启动 TensorBoard 查看训练曲线
tensorboard --logdir runs/

TensorBoard 分析要点

  • episode_reward_mean：平均奖励，应该随训练逐步上升
  • episode_length_mean：平均 episode 长度，反映智能体存活能力
  • loss/policy 和 loss/value：策略和价值损失，应该稳定下降
  • entropy：策略熵，反映探索程度，不应过快降到0

机械臂与抓取 Demo 讲解
60 分钟 机械臂

Franka 抓取任务

franka-lift-cube 任务：控制 Franka 机械臂抓取并抬起一个立方体。核心难点：

  • 末端执行器的精确位置控制
  • 抓取时的接触力控制
  • 多关节协调运动
  • 奖励设计需要同时考虑"到达"、"抓取"和"抬起"三个阶段

奖励设计思路

  • 到达奖励：末端执行器接近立方体的距离奖励
  • 抓取奖励：夹爪闭合且接触立方体
  • 抬起奖励：立方体高度提升
  • 稳定奖励：保持立方体在空中

Franka 打开抽屉任务对比

要素franka-lift-cube打开抽屉

奖励设计对策略的影响

  • 速度奖励为主：机器人会学习快速奔跑，但可能牺牲稳定性
  • 能量惩罚为主：机器人会学习节能步态，动作幅度小
  • 平衡奖励为主：机器人会学习保守步态，避免摔倒
  • 综合奖励：需要仔细调权重，才能得到自然步态

修改 Demo 的完整流程

  1. 理解原 Demo：用 8 要素法分析任务目标、观测、动作、奖励、终止条件
  2. 确定修改点：明确要改什么（奖励？目标位置？动作尺度？）
  3. 修改配置：在 EnvCfg 中调整相关参数
  4. 修改实现：在 Env 或 Reward 中修改逻辑
  5. 注册验证：确保修改后的环境能被框架正确识别
  6. 训练测试：运行训练，观察效果
  7. 迭代优化：根据训练结果继续调整

开发新任务的步骤

  1. 准备机器人模型文件（URDF/MJCF）
  2. 创建 EnvCfg，定义环境参数
  3. 创建 Env 类，实现任务逻辑
  4. 创建 Reward 类，设计奖励函数
  5. 注册到 motrix_envs.registry
  6. 创建 RLCfg，配置训练参数
  7. 注册到 motrix_rl.registry
  8. 修改 import 链，确保框架能自动加载
  9. 运行训练，调试优化

第一期核心修正案例

问题根源：原版 Motrix 以 actuator_ctrl_limits（物理限位）作为动作空间边界，配合 action_scale=0.05。后续调参时将 action_scale 改为 0.25，但未同步修改动作空间边界。

实际影响：calf 关节动作空间异常（范围全为负值），与归一化动作空间语义不等价。

修正方案：

python
# 修正前：以物理限位作为边界
gym.spaces.Box(actuator_ctrl_limits[0], actuator_ctrl_limits[1], ...)

# 修正后：固定归一化范围
gym.spaces.Box(-np.ones(n), np.ones(n), ...)
